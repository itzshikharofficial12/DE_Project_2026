## 1. Objective

The objective of Phase 3 is to establish a rigorous, reproducible **baseline query performance profile** for all 30 workload queries (`R01`–`R25` read queries and `W01`–`W05` write queries) defined in [`queries/workload_30.sql`](../queries/workload_30.sql) against the unoptimized Phase 2 relational schema (`dream11`).

In this baseline state, the database contains **zero manually tuned performance indexes**—only the 18 automatic B-tree indexes generated by PostgreSQL to enforce the 10 `PRIMARY KEY` and 8 `UNIQUE` constraints from [`sql/01_schema.sql`](../sql/01_schema.sql). Measuring execution plans, buffer accesses, scan operators, and execution latencies across 3 independent runs per query provides the empirical reference point against which all Phase 4 index additions and query rewrites will be evaluated.

## 3. Benchmark Methodology

1. **Automated Query Extraction & Execution:**
   The script [`benchmarks/run_benchmark.sh`](../benchmarks/run_benchmark.sh) splits [`queries/workload_30.sql`](../queries/workload_30.sql) on `-- @R01` through `-- @W05` markers into 30 individual SQL files and executes each query 3 consecutive times via `psql -X` (ignoring any local `.psqlrc`).
2. **Why Three Repetitions per Query:**
   Running each query 3 times captures both initial buffer/cache warm-up effects (Run 1) and steady-state in-memory execution (Runs 2 and 3), reducing sensitivity to transient OS scheduling jitter.
3. **Execution Time & Buffer Capture:**
   Every query is executed with `EXPLAIN (ANALYZE, BUFFERS)`. This runs the query to completion inside PostgreSQL's executor, reports actual row counts and loop iterations per plan node, records shared/temp buffer hits, reads, and dirtied pages (`Buffers: shared hit=...`), and outputs the exact server-side `Execution Time: <ms> ms`. All 3 full execution plans per query are saved in `benchmarks/results/baseline/<query_id>.txt`.
4. **Arithmetic Average Calculation:**
   For each query, `average_ms` (`avg_ms` in [`benchmarks/results/baseline/summary.csv`](../benchmarks/results/baseline/summary.csv)) is computed as the arithmetic mean of the three measured execution times rounded to 3 decimal places:
   $$\text{Average (ms)} = \frac{\text{Run 1} + \text{Run 2} + \text{Run 3}}{3}$$
5. **Write Query Isolation & Rollback Strategy:**
   Every write query (`W01`–`W05`) is wrapped in an explicit transaction block that rolls back immediately after `EXPLAIN (ANALYZE, BUFFERS)` completes:
   ```sql
   SET search_path TO dream11;
   BEGIN;
   EXPLAIN (ANALYZE, BUFFERS) <write_query>;
   ROLLBACK;
   ```
   This ensures that PostgreSQL performs the real tuple insertions/updates, index maintenance, and constraint checks during timing measurement, while `ROLLBACK` restores the database state so subsequent runs and tables remain completely unmodified.

## 5. Performance Observations

### 1. Fastest Queries (Under 0.5 ms)

The five fastest queries in the baseline workload all benefit directly from PostgreSQL's automatic `PRIMARY KEY` and `UNIQUE` constraint B-tree indexes (or operate on tiny 450-row tables):

1. **R23 (`0.029 ms` avg):** Point lookup on `users.phone` using `uq_users_phone` (`Index Scan`, 4 shared buffers).
2. **R03 (`0.037 ms` avg):** Prefix lookup on `(user_id, match_id)` via `uq_user_teams_user_match_label` followed by two PK lookups on `pk_players` (12 shared buffers).
3. **R07 (`0.078 ms` avg):** Exact match on `(user_id, match_id, team_label)` via `uq_user_teams_user_match_label`, 11 roster rows via `pk_user_team_players`, and 11 PK lookups on `pk_players` and `pk_player_match_stats` (105 shared buffers).
4. **R16 (`0.134 ms` avg):** Sequential scan over 450 `players` and 18 `teams` (5 shared buffers).
5. **R04 (`0.183 ms` avg):** Scans 2,544 `contests` (29 buffers) and uses `uq_contest_entries_contest_team` for the 11 contests of match 207 (63 total buffers).

### 2. Slowest Queries & Dominant Bottlenecks

The total baseline execution time across all 30 queries is **`2,468.442 ms`**, and a single outlier query accounts for **88.7%** of the entire workload runtime:

1. **R19 (`2,190.351 ms` avg — 88.7% of total time):**
   - **Evidence from Plan:** `R19` selects the 250 IPL (`FRANCHISE`) players and runs a correlated scalar subquery `(SELECT count(*) FROM user_team_players utp WHERE utp.player_id = p.player_id)` for each player. Because `pk_user_team_players` is defined on `(user_team_id, player_id)` with `player_id` as the *second* column, PostgreSQL cannot efficiently seek by `player_id` alone and chooses `Seq Scan on user_team_players` inside `SubPlan 1` (`loops=250`), touching **`500,008` shared buffers** (`~3.8 GB` of buffer reads in memory) and evaluating ~110 million rows.
2. **R06 (`52.354 ms` avg):**
   - **Evidence from Plan:** For the 278 teams in match 183 (`3,062` player selections), the `CROSS JOIN LATERAL` subquery executes **3,062 loops**, performing 3,062 sequential scans of `players` (`12,248` buffers) and 3,062 index-only scans on `pk_user_team_players` (`9,187` buffers), totaling **`22,671` shared buffers**.
3. **R02 (`39.264 ms` avg):**
   - **Evidence from Plan:** Lacking an index on `user_teams(match_id)`, PostgreSQL scans `user_teams` (39,975 rows) twice (once in `InitPlan 1` and once in the main query) and performs a `Merge Right Join` against an `Index Only Scan` of almost the entire 439,925-row `pk_user_team_players` index (`437,460` rows scanned, `2,007` shared buffers).
4. **R22 (`26.522 ms` avg):**
   - **Evidence from Plan:** `ORDER BY created_at DESC OFFSET 50000 LIMIT 25` on `wallet_transactions` has no index on `created_at`, forcing a full sequential scan of 118,343 rows and an **external disk merge sort** (`Sort Method: external merge Disk: 5800kB`, `temp read=530 written=727`).
5. **R15 (`19.865 ms`), R13 (`18.175 ms`), R11 (`17.773 ms`), R17 (`14.554 ms`), W04 (`13.417 ms`):**
   - Each of these queries performs full sequential scans across one or more of the large tables (`wallet_transactions`: 118,343 rows; `users`: 50,000 rows; `contest_entries`: 42,746 rows; `user_teams`: 39,975 rows) due to missing foreign-key and filter indexes.

### 3. Run-to-Run Variation Analysis

- **Cold-to-Warm Buffer Stabilization:** Several queries show slightly higher execution time on Run 1 followed by tighter, faster timings on Runs 2 and 3:
  - **R02:** `56.508 ms` (Run 1) → `33.284 ms` (Run 2) → `27.999 ms` (Run 3). In Run 1, `Planning Time` was `3.834 ms` and the sort/merge over 437k index entries warmed CPU caches; Runs 2 and 3 stabilized around ~28–33 ms.
  - **R06:** `65.143 ms` (Run 1) → `45.949 ms` (Run 2) → `45.969 ms` (Run 3). Runs 2 and 3 are virtually identical (`0.020 ms` difference).
  - **W04:** `18.693 ms` (Run 1) → `12.372 ms` (Run 2) → `9.186 ms` (Run 3).
- **High Consistency on Large Scans:** Queries dominated by large sequential buffer scans or external sorts (`R09`, `R10`, `R12`, `R14`, `R15`, `R17`, `R18`, `R19`, `R20`, `R21`, `R22`, `R25`, `W05`) showed very low relative variance (<10% spread across all 3 runs).

### 4. Critical Logic / Correctness Finding Observed in Baseline (`R13`)

While inspecting the `EXPLAIN (ANALYZE, BUFFERS)` plan for **R13** (*Finance audit: paid contest entries that have no entry-fee debit in the wallet*), we confirmed why Problem **P5** in the project brief states *"The finance audit of paid entries with no wallet debit always comes back empty—impossible"*:
- In [`benchmarks/results/baseline/R13.txt`](../benchmarks/results/baseline/R13.txt), the node `Seq Scan on contest_entries ce` applies `Filter: (NOT (ANY (entry_id = (hashed SubPlan 1).col1)))`, which removes all **42,746 rows** (`actual time=19.640..19.641 rows=0 loops=1`).
- Because `wallet_transactions.reference_entry_id` is `NULL` for 63,000 rows (`DEPOSIT`, `BONUS`, `WITHDRAWAL`), the SQL expression `ce.entry_id NOT IN (SELECT w.reference_entry_id FROM wallet_transactions w)` evaluates `ce.entry_id <> NULL`, which yields `UNKNOWN` (falsy in `WHERE`) for every row!
- As verified in our Phase 2 integrity check, there are actually **192 paid contest entries** with no wallet debit. Rewriting `NOT IN` to `NOT EXISTS` (or filtering `WHERE w.reference_entry_id IS NOT NULL`) will be a key correctness and performance fix in Phase 4.

### 5. Hypotheses & Candidate Optimizations for Phase 4

Based strictly on the scan bottlenecks observed in the baseline `EXPLAIN (ANALYZE, BUFFERS)` plans, we formulate the following testable hypotheses for Phase 4:

1. **Foreign-Key & Reversed Composite Indexes:**
   - Adding an index on `user_team_players(player_id)` (or `(player_id, user_team_id)`) and rewriting **R19** from a correlated subquery to a `LEFT JOIN ... GROUP BY` is hypothesized to eliminate the 250× sequential scan of `user_team_players` (`500,008` buffers) and reduce **R19** from `~2,190 ms` to single-digit milliseconds.
   - Adding an index on `user_teams(match_id)` (with covering columns such as `captain_id`, `user_team_id`) is hypothesized to eliminate the full sequential scans of `user_teams` in **R02**, **R06**, **R08**, **W02**, and **W04**.
2. **Query Rewrites for Correlated & Non-Sargable Patterns:**
   - **R06 (`52.354 ms`):** Rewriting the `CROSS JOIN LATERAL` (which runs 3,062 loops) into a two-stage window function or pre-grouped CTE per `(user_team_id, team_id)` is hypothesized to drop buffer hits from `22,671` to under `1,500`.
   - **R13 (`18.175 ms`):** Replacing `NOT IN` with `NOT EXISTS` (and indexing `wallet_transactions(reference_entry_id)`) will both fix the `NULL` correctness bug (returning the 192 unpaid entries) and allow an indexed anti-join.
   - **R14 (`10.745 ms`):** Pre-aggregating entry counts per `contest_id` before joining to `contests` avoids `count(DISTINCT ...)` / `sum(DISTINCT ...)` sorting across 18,452 rows (and avoids the `sum(DISTINCT c.total_spots)` trap when two contests in the same type share the same `total_spots`!).
   - **R20 (`6.565 ms`):** Rewriting `created_at::date BETWEEN '2026-06-01' AND '2026-06-30'` into a sargable `TIMESTAMPTZ` range (`created_at >= '2026-06-01 00:00:00+05:30' AND created_at < '2026-07-01 00:00:00+05:30'`) will allow a B-tree index scan on `(txn_type, status, created_at)`.
3. **Targeted Wallet & Compliance Indexes:**
   - Indexing `wallet_transactions(user_id, status, created_at, txn_id) INCLUDE (txn_type, amount)` for **R09** (`5.611 ms` → target `< 1 ms`) and **R18**.
   - Indexing `wallet_transactions(created_at DESC)` for **R22** (`26.522 ms`) to eliminate the `5,800 kB` external disk sort, plus partial indexing on `wallet_transactions(created_at) WHERE txn_type = 'WITHDRAWAL' AND status = 'PENDING'` for **R10** and **W05**.
